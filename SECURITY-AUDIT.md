## 2. Найденные уязвимости

Статусы: 🔴 Critical · 🟠 High · 🟡 Medium · 🟢 Low

### F-01 🔴 Обход блокировки `/backend` → утечка токенов, пароля и ПДн  ✅ ЗАКРЫТО

`_blocked()` сравнивал префикс с **сырым** `self.path`, а `translate_path()`
из стандартной библиотеки декодирует `%2e%2e` → `..` и схлопывает путь **после**
этой проверки.

Подтверждено на стенде до правки:

```
GET /img/%2e%2e/backend/bot_token.txt   → HTTP 200  «1234567890:FAKE_TOKEN_…»
GET /img/%2e%2e/backend/app.py          → HTTP 200  PASSWORD = "Adminka!2000"
GET /img/%2e%2e/backend/leads.json      → HTTP 200  все имена и телефоны клиентов
GET /img/%2e%2e/backend/chats.json      → HTTP 200  chat_id администраторов
```

`curl /img/../backend/...` не срабатывает (curl нормализует путь сам), а закодированный
вариант — срабатывает, и nginx такие пути пробрасывает без изменений.

**Цепочка эскалации:** токен бота → полный захват бота (чтение и удаление всех заявок,
сообщения админу от имени питомника). Исходник → пароль админки → вход в бота админки →
вся база клиентов. Утечка персональных данных по 152-ФЗ.

**Закрытие** (`_is_servable()` + `translate_path()` в `backend/app.py`): путь сначала
разрешается тем же алгоритмом, что и у stdlib, затем проверяется **результат** —
`realpath` обязан лежать внутри web-root, первый компонент не входит в `DENIED_DIRS`,
расширение не входит в `DENIED_SUFFIXES`, скрытые файлы не отдаются. Дополнительно
отключён листинг каталогов (`list_directory()`).

Проверено после правки — все варианты дают 404:

```
/backend/bot_token.txt              404      /img/%2e%2e/backend/bot_token.txt   404
/img/%2E%2E/backend/app.py          404      /./backend/app.py                   404
//backend/chats.json                404      /css/%2e%2e/backend/chats.json      404
/img/..%2fbackend/bot_token.txt     404      /tools/build_catalog.py             404
/.gitignore                         404      /img/ (листинг)                     404
```

Легитимный контент не пострадал: `/`, `/index.html`, `/catalog.html`, `/offer.html`,
`/privacy-policy.html`, `/css/style.css`, `/js/main.js`, `/img/logo.png`, ЧПУ
`/privacy-policy` и `/offer` — все 200.

> **Две регрессии, которые вскрыла проверка и которые исправлены.**
>
> 1. Первая версия `_is_servable()` сломала главную страницу: `relpath(ROOT, ROOT)`
>    возвращает `.`, и проверка скрытых файлов отклоняла сам корень — `/` отдавал 404.
>    Исправлено: корень обрабатывается отдельно через `os.curdir`.
> 2. Запрет скрытых путей закрыл `/.well-known/acme-challenge/`, то есть сломал бы
>    продление сертификата Let's Encrypt, если nginx проксирует ACME-проверки
>    в приложение. Добавлено узкое исключение: разрешён только
>    `.well-known/acme-challenge/<файл>`, проверка выхода за web-root выполняется
>    до него. Проверено — обход не появляется:
>
> ```
> /.well-known/acme-challenge/testtoken                    200  (содержимое отдаётся)
> /.well-known/acme-challenge/%2e%2e/backend/bot_token.txt 404
> /.well-known/                                            404
> /.env  ·  /.hidden-dir/x.txt  ·  /.gitignore              404
> ```

### F-02 🔴 Пароль администратора захардкожен в исходнике  ✅ ЗАКРЫТО

`PASSWORD = "Adminka!2000"` на строке 42. В паре с F-01 давал полный доступ к базе
клиентов одним запросом. Пароль также попадал в любой бэкап и в историю VCS.

**Закрытие:** значение берётся только из `ADMIN_PASSWORD`. Пустой пароль означает
«вход закрыт для всех», а не «подходит пустая строка». Сравнение переведено на
`hmac.compare_digest` по UTF-8 байтам — прежний `==` позволял подбирать пароль
посимвольно по времени ответа.

### F-03 🔴 Секреты и ПДн лежат внутри web-root  ⚠️ ЧАСТИЧНО (нужны действия на сервере)

`bot_token.txt`, `admin_token.txt`, `admin_chat_ids.txt`, `leads.json`, `chats.json`
находятся в `backend/` — подкаталоге web-root. F-01 закрыт, и файлы больше не отдаются,
но защита остаётся однослойной: любая будущая ошибка маршрутизации снова откроет их.

**Сделано:** `.gitignore` исключает токены, `leads.json`, `chats.json`, `.env`.
Права на файлы токенов уже `0600`.

**Осталось сделать на сервере** (см. чек-лист, раздел 7): вынести каталог данных за
пределы web-root и задать `DATA_DIR`, либо оставить как есть и полагаться на
`DENIED_DIRS` + nginx. Рекомендуемый вариант — вынести.

### F-04 🟠 XSS-синки в `js/main.js`  ✅ ЗАКРЫТО

Два места вставляли непроверенные значения в HTML-строку:

- строка 214, `orderRow()` — `row.insertAdjacentHTML("beforeend", …${item.name}…)`
- строка 317 — `controls.innerHTML = …${name}…`

Источники значений не полностью доверены:

1. `localStorage` (`loadCart()` принимает произвольные строки) — отравление хранилища;
2. `data-name` в `catalog.html`, который **скрейпится со стороннего сайта**
   `green-dvorik.ru` из JSON-LD (`tools/build_catalog.py`). Изменение или компрометация
   чужого каталога даёт stored XSS на сайте питомника.

Значение из атрибута попадает в `dataset.name` уже **раскодированным**, поэтому
`escape()` на этапе сборки каталога не защищает: `data-name="Туя 15&quot; onload=…"`
даст кавычку, закрывающую атрибут `aria-label`.

**Закрытие:** добавлена `escapeHtml()` (экранирует `& < > " '`), применена во всех
подстановках обоих синков. Значения, вставляемые через `textContent`
(название и цена в `orderRow`), не менялись — они и так безопасны.

### F-05 🟠 Отсутствуют все security-заголовки  ✅ ЗАКРЫТО

Проверка до правки — не найдено ни одного:

```
ОТСУТСТВУЕТ: Content-Security-Policy      ОТСУТСТВУЕТ: X-Content-Type-Options
ОТСУТСТВУЕТ: X-Frame-Options              ОТСУТСТВУЕТ: Strict-Transport-Security
ОТСУТСТВУЕТ: Referrer-Policy              ОТСУТСТВУЕТ: Permissions-Policy
```

**Закрытие:** заголовки добавляются в `end_headers()`, через который проходят статика,
JSON и страницы ошибок — пропусков не бывает.

После правки:

```
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin
Permissions-Policy: geolocation=(), microphone=(), camera=(), payment=()
Cross-Origin-Opener-Policy: same-origin
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'
  https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com;
  img-src 'self' data: https://images.unsplash.com; connect-src 'self';
  object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'
```

CSP **без `'unsafe-inline'`** — для этого единственный inline-стиль на страницах
(`style="position:absolute"` у SVG-спрайта) заменён классом `.svg-sprite`.
`frame-ancestors 'none'` дублирует `X-Frame-Options` и защищает от clickjacking.

`Strict-Transport-Security` отправляется только при `PUBLIC_HTTPS=1`: HSTS по открытому
HTTP браузеры игнорируют, а включить его до перехода на HTTPS — значит зафиксировать
заголовок впустую. Основной источник HSTS — nginx (раздел 4).

### F-07 🟠 Нет ограничения размера тела запроса  ✅ ЗАКРЫТО

```python
length = int(self.headers.get("Content-Length", 0))
raw = json.loads(self.rfile.read(length).decode("utf-8"))
```

Память выделялась под объявленный `Content-Length` до какой-либо проверки.
Подтверждено: тело 20 МБ было прочитано целиком и лишь затем отклонено как 400.
Отрицательное или нечисловое значение приводило к исключению.

**Закрытие:** `MAX_BODY_BYTES` (по умолчанию 32 КБ) проверяется **до** чтения,
ответ `413 Payload Too Large`, соединение закрывается. Отрицательные и
нечисловые значения отклоняются тем же кодом.

Проверено: тело ~2 МБ → 413, `Content-Length: 5000000000` → 413 без выделения памяти.

Дополнительно `ThreadingHTTPServer` заменён на `BoundedServer` с потолком
одновременных подключений `MAX_CONCURRENCY` (64) и ответом 503 при исчерпании —
штатный сервер плодит поток на каждый запрос без ограничения.

### F-08 🟡 Honeypot не работал  ✅ ЗАКРЫТО

Бэкенд проверял `raw.get("website")`, но `js/main.js` **никогда не отправлял** это поле:
`submitLead()` собирал payload перечислением полей, и `website` среди них не было.
Поле присутствовало только в одной форме из семи (`#ctaForm` на `index.html`),
в модалках `callbackForm` и `cartOrderForm` его не было вовсе.

**Закрытие:** honeypot добавлен во все формы всех четырёх страниц

`privacy-policy.html` — по 2/2), `submitLead()` передаёт значение, в CSS введён общий

Проверено: заполненный honeypot → `{"ok": true, "id": 0}`, заявка в базу не попадает,
в журнале событие `honeypot_hit`. Ответ намеренно неотличим от успешного — бот не
должен узнавать, по какому признаку его отсекли.

### F-09 🟡 Нет проверки времени заполнения формы  ✅ ЗАКРЫТО

**Закрытие:** `main.js` запоминает момент, когда форма стала доступна
(`markFormsOpened()` при загрузке страницы и при каждом открытии модалки), и передаёт
`elapsed_ms`. Бэкенд отклоняет отправку быстрее `MIN_FILL_SECONDS` (2 с), включая
случаи отсутствующего, строкового или булева значения поля.

Проверено: `elapsed_ms=300` → `id: 0`; `elapsed_ms` отсутствует → `id: 0`;
`elapsed_ms="99999"` (строка) → `id: 0`; `elapsed_ms=12400` → заявка принята.

Отсутствующее значение отклоняется намеренно: спамер, который отправляет POST
напрямую без JavaScript, поле просто не передаст. Если принимать «поля нет» как норму,
проверка перестаёт работать ровно против той угрозы, от которой введена.

> ⚠️ **Требование к деплою: фронтенд и бэкенд выкатываются вместе.**
> Это изменение контракта между `main.js` и `/api/lead`. Посетитель, у которого
> в кеше осталась старая страница со старым `main.js?v=15`, не пришлёт `elapsed_ms`,
> и его заявка будет отброшена — при этом форма покажет «Спасибо за заявку».
> Версии ассетов подняты (`main.js?v=16`, `style.css?v=30`), HTML при деплое меняется
> и браузеры его перевалидируют, поэтому окно риска измеряется минутами.
> Деплойте в часы низкого трафика и сразу после выкладки следите в журнале за событием
> `legacy_client` — оно отделено от `too_fast_submit` именно для этого: всплеск
> означает, что часть клиентов ещё не получила новую версию.
>
> ```
> [WARNING] security: legacy_client ip=… elapsed_ms=None
> ```

> **Риск ложных срабатываний `too_fast_submit`:** отсчёт начинается не от фокуса в
> поле, а от открытия модалки (или загрузки страницы для формы в CTA), поэтому
> автозаполнение браузера не укладывается в порог. Если таких событий много от реальных
> клиентов, уменьшите `MIN_FILL_SECONDS`.

### F-11 🟡 CSV-инъекция в экспорте заявок  ✅ ЗАКРЫТО

### F-12 🟡 Rate limiting неполный и с утечкой памяти  ✅ ЗАКРЫТО

Проблемы до правки:

- лимит 5 запросов/мин применялся **только** к `/api/lead`; статика не ограничивалась
  вообще — подтверждено: 30/30 запросов `catalog.html` → 200 (скрейпинг каталога);
- проверка вызывалась **после** разбора тела запроса, то есть после выделения памяти;
- словарь `RATE` никогда не очищался: каждый новый IP добавлял запись навсегда
  (неограниченный рост памяти);
- использовался `client_address[0]`, то есть за nginx все клиенты имели бы один IP.

**Закрытие:** три раздельных лимита со скользящим окном, очистка устаревших корзин,
потолок числа отслеживаемых ключей, определение реального IP через `X-Forwarded-For`
только от доверенного прокси.

| Лимит | По умолчанию | Что ограничивает |
|---|---|---|
| `public` | 60/мин | HTML-документы и `/api/lead` |
| `asset` | 600/мин | изображения, CSS, JS |
| `lead` | 5/час | заявки — по IP **и** по нормализованному телефону |

> **Осознанное отступление от ТЗ.** ТЗ требует 60 req/min на публичных эндпоинтах.
> Применять этот порог к каждому файлу нельзя: одна страница каталога запрашивает
> HTML + CSS + JS + около сотни изображений, то есть ~103 запроса, и сайт не отрисовался
> бы ни у одного посетителя. Поэтому статика вынесена в отдельный лимит `asset`,
> а 60/мин сохранены для документов и API — именно они интересны скрейперу.

Проверено при `LEAD_LIMIT_PER_HOUR=3`: заявки 1–3 → 200, заявки 4–5 → 429.
Разные `X-Forwarded-For` попадают в разные корзины — учёт за прокси работает.

---

### F-13 🟡 Переиспользование id заявок (аналог IDOR)  ✅ ЗАКРЫТО

`"id": len(LEADS) + 1` — после удаления заявки следующий клиент получал id удалённой.
Кнопки бота (`lead:<id>:done`, `ledit:<id>`, `ldel:<id>`) правили бы чужую запись.

**Закрытие:** монотонный счётчик `NEXT_ID`, инициализируется как
`max(существующие id) + 1`, поэтому не сбрасывается и не переиспользуется после
перезапуска. Проверено: после 33 заявок и перезапуска процесса следующая получила id 34;
в финальном прогоне id уникальны, диапазон 1–33 без пропусков и коллизий.

---

### F-14 🟢 SSRF в сборщике каталога  ✅ ЗАКРЫТО

`tools/build_catalog.py::download_image()` скачивал произвольный URL из поля
`image.contentUrl` чужого JSON-LD без проверки. Подмена адреса на
`http://169.254.169.254/latest/meta-data/` или `http://127.0.0.1:8000/...` заставила бы
скрипт сходить во внутреннюю сеть с правами запустившего его пользователя.
Это и есть случай «загрузка фото по URL» из A10 — на бэкенде такой функции нет.

**Закрытие:** `assert_public_url()` отклоняет схемы кроме http/https и адреса
private / loopback / link-local / reserved / multicast / unspecified (разрешение имени
через `getaddrinfo`, проверяются **все** полученные адреса). Добавлен потолок размера
ответа (`MAX_IMAGE_BYTES`, 15 МБ; для страниц — `MAX_PAGE_BYTES`, 10 МБ).

Ограничение зафиксировано в комментарии к функции: между разрешением имени и
подключением адрес может смениться (DNS rebinding). Для офлайн-сборщика каталога риск
приемлем; при переносе логики в бэкенд потребуется привязка к разрешённому IP.

---

### F-15 🟢 Предсказуемый кеш в общем `/tmp`  ✅ ЗАКРЫТО

`CACHE_DIR = "/tmp"` с именами `cat-<ключ>.html` и `src-<slug>.jpg`. Другой локальный
пользователь мог заранее создать симлинк или подменить содержимое — запись шла бы по
чужому пути.

**Закрытие:** кеш перенесён в `<project>/.cache` с правами `0700`
(`ensure_cache_dir()`), каталог исключён из VCS.

---

### F-16 🟢 Необработанное исключение на поддельных `callback_data`  ✅ ЗАКРЫТО

`int(data[5:])` для `ldel:` и `int(data[6:])` для `ledit:` вызывались без проверки.
`callback_data` формирует клиент Telegram и подделывается, поэтому `ldel:abc` давал
`ValueError`. Процесс не падал (исключение перехватывал цикл бота), но ветка
обработки прерывалась, а в журнал шла трассировка.

**Закрытие:** `parse_lead_id()` — только цифры, длина до 9, иначе `None`;
вызывающий код фиксирует событие `bad_callback_data`.

---

### F-17 🟡 Журналирование безопасности отсутствовало  ✅ ЗАКРЫТО

Неудачные попытки входа, отказы валидации и подозрительные запросы не фиксировались.

**Закрытие:** отдельный логгер `security`, события:

```
bot_login_ok / bot_login_failed / bot_login_blocked / bot_login_misconfigured
path_denied · bad_user_agent · empty_user_agent · rate_limited
honeypot_hit · too_fast_submit · legacy_client · body_too_large · concurrency_limit
rejected_name / rejected_phone / rejected_payload · bad_callback_data · lead_anomaly
```

Все события подтверждены на стенде фактическими записями журнала:

```
[WARNING] security: path_denied ip=127.0.0.1 path=/img/%2e%2e/backend/bot_token.txt
[WARNING] security: bad_user_agent ip=127.0.0.1 ua=curl/8.7.1
[WARNING] security: honeypot_hit ip=127.0.0.1
[WARNING] security: too_fast_submit ip=127.0.0.1 elapsed_ms=120
[WARNING] security: body_too_large ip=127.0.0.1 length=100172
```

**Пароли и токены не логируются:** в журнал пишется факт попытки входа, но не введённый
текст; `clean_for_log()` вырезает переводы строк, поэтому пользовательские данные не
могут подделать строку журнала. Проверено поиском по журналу: ни пароль, ни токен в нём
не встречаются.

**Алерт об аномалии (A09):** `alert_if_anomaly()` считает заявки за последний час и при
превышении `LEAD_ALERT_THRESHOLD` (100) пишет событие и уведомляет активированные чаты
бота админки — не чаще раза в час.

### F-18 🟡 Скрейпинг каталога не ограничен  ✅ ЗАКРЫТО

**Закрытие:** лимит `public` на HTML-документы (F-12) + фильтр User-Agent
(`BAD_UA_RE`) на всех эндпоинтах.

Проверено:

```
curl/8.7.1 (UA по умолчанию)   → 403
пустой User-Agent              → 403
python-requests/2.31           → 403
Mozilla/5.0 … Chrome/120       → 200
Mozilla/5.0 (YandexBot/3.0)    → 200
```

> Поисковые роботы в блок-лист **не** входят: индексация каталога должна работать.
> Список настраивается правкой `BAD_UA_RE`. Блокировка по UA обходится тривиально —
> это снижение шума от примитивных скрейперов, а не защита; основной барьер — лимиты.

## 4. Конфигурация nginx

Отдельные файлы развёртывания по согласованию не создавались — конфигурация приведена
здесь. Приложение слушает `127.0.0.1:8000` и не должно быть доступно из интернета
напрямую.

```nginx
# /etc/nginx/conf.d/green-dvorik.conf

# Зоны ограничения частоты. burst с nodelay гасит всплески при загрузке страницы.
limit_req_zone $binary_remote_addr zone=per_ip:10m   rate=30r/m;
limit_req_zone $binary_remote_addr zone=assets:10m   rate=300r/m;
limit_conn_zone $binary_remote_addr zone=per_conn:10m;

# HTTP → HTTPS
server {
    listen 80;
    listen [::]:80;
    server_name green-dvorik.ru www.green-dvorik.ru;
    # ACME-проверки Let's Encrypt обслуживаются до редиректа
    location /.well-known/acme-challenge/ { root /var/www/certbot; }
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    http2 on;
    server_name green-dvorik.ru www.green-dvorik.ru;

    ssl_certificate     /etc/letsencrypt/live/green-dvorik.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/green-dvorik.ru/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers off;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 1d;
    ssl_session_tickets off;

    # A05: не раскрывать версию nginx
    server_tokens off;

    # Размер тела — тот же потолок, что и в приложении (32 КБ)
    client_max_body_size 32k;
    client_body_timeout  10s;
    client_header_timeout 10s;
    send_timeout         10s;

    limit_conn per_conn 20;

    # A05: заголовки. HSTS включается только на HTTPS-сервере.
    # Приложение тоже их отправляет; дубли совпадают по значениям.
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Frame-Options           "DENY"                               always;
    add_header X-Content-Type-Options    "nosniff"                            always;
    add_header Referrer-Policy           "strict-origin"                      always;

    root /var/www/green-dvorik;

    # Статика с длинным кешем; версия в ?v= обеспечивает инвалидацию
    location ~* \.(?:jpg|jpeg|png|webp|avif|gif|svg|ico|css|js|woff2?)$ {
        limit_req zone=assets burst=200 nodelay;
        expires 30d;
        add_header Cache-Control "public, immutable";
        try_files $uri =404;
    }

    # Запрет доступа к служебным каталогам — второй слой поверх DENIED_DIRS
    location ~ ^/(backend|tools|\.)/ { return 404; }

    location /api/ {
        limit_req zone=per_ip burst=10 nodelay;
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        # КРИТИЧНО: перезаписывать, а не дополнять.
        # $proxy_add_x_forwarded_for склеивает значение клиента со своим, и
        # посетитель сможет подставить чужой IP, обходя лимиты приложения.
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Host              $host;
        proxy_set_header Connection        "";
        proxy_read_timeout 30s;
    }

    location / {
        limit_req zone=per_ip burst=20 nodelay;
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Host              $host;
        proxy_set_header Connection        "";
    }
}
```

После включения TLS запустите приложение с `PUBLIC_HTTPS=1` и
`TRUSTED_PROXIES=127.0.0.1,::1`.

**Прочая инфраструктура (ЗАДАЧА 3)** — на уровне сервера, в коде не отражается:

```bash
# Fail2ban: брутфорс SSH и HTTP-флуд
apt install fail2ban
# /etc/fail2ban/jail.d/green-dvorik.local
#   [sshd]    enabled = true, maxretry = 3, bantime = 1h
#   [nginx-limit-req] enabled = true, filter = nginx-limit-req,
#                     logpath = /var/log/nginx/error.log, maxretry = 10

# Firewall: только SSH, HTTP, HTTPS
ufw default deny incoming && ufw default allow outgoing
ufw allow OpenSSH && ufw allow 80/tcp && ufw allow 443/tcp && ufw enable

# Автообновления безопасности ОС
apt install unattended-upgrades && dpkg-reconfigure -plow unattended-upgrades
```

**База данных.** В проекте JSON-файлы, поэтому пункты ТЗ про отдельного пользователя БД
с минимальными правами и доступ только с localhost неприменимы. Эквивалент для файлов:
владелец `www-data`, права `0600` на `leads.json`/`chats.json` и `0700` на каталог,
доступ только пользователю сервиса.

```bash
chown -R www-data:www-data /var/lib/green-dvorik
chmod 0700 /var/lib/green-dvorik && chmod 0600 /var/lib/green-dvorik/*.json
```

**Бэкапы** (ежедневно, шифрование, хранение вне сервера):

```bash
# /etc/cron.daily/green-dvorik-backup
tar -C /var/lib -czf - green-dvorik \
  | gpg --symmetric --cipher-algo AES256 --batch --passphrase-file /root/.backup-key \
  > /var/backups/gd-$(date +%F).tar.gz.gpg
# затем — выгрузка в S3/Backblaze и удаление локальных копий старше 7 дней
```

**Загрузка файлов.** Не реализована: конвертация в WebP через Pillow, проверка
MIME через `python-magic`, X-Sendfile и имена на uuid не применяются — загружать
на сайт нечего (см. раздел 5, A08).
